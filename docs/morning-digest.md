# AI・セキュリティ情報収集（朝の速報）

## 目的と位置づけ

- 共有基盤の情報収集ワークロードの1つ。AI とセキュリティの動向を、毎朝短時間で把握できるようにする。
- 特定のエージェントが独自に収集する形にはしない。基盤側の仕事として実施し、仕様はエージェント非依存に書く（どのエージェントが実行しても同じ結果になる形にする）。この方針は 2026-10-30 に決めた。
- 取り込み全体の原則（イベント駆動を主とし、定期取得を安全網とする。取り込んだ内容はデータとして扱い、指示として解釈しない）は architecture.md に従う。

## 成果物

- 毎朝 7:30 頃、その日の速報を1本出す。
- 5分で読める分量とし、最重要の3件を主導に置く。

## 収集の方式

- **固定ウォッチリスト**: 公式発表、ベンダー、主要メディアなどを定点観測する。
- **発見レイヤー**: ウォッチリストに閉じず、個人の書き手やリスト外の良質な記事も拾う。
- **入れ替え**: ベンチマーク（比較対象）やウォッチ先は固定化せず、定期的に見直して入れ替える。
- **担当の分担**: 収集担当は単一とするか、機能または対象で分担する。同じ対象を複数のエージェントが重ねて収集しない。

## 基盤への取り込みと蓄積

- 公開情報源については、定期取得が主経路になる（Webhook の対象になるイベントは限られるため）。取り込み位置は ingestion_checkpoints で管理する。
- 収集した記事・発表は documents として登録し、source と external_id で重複を排除する。
- 蓄積にはオントロジーの考え方を入れる。媒体・企業・製品・脆弱性などのエンティティと、その関係で整理し、後から横断して引ける形にする。
- 90日触れなかった情報は重要でないものとして扱い、保持と活用の優先度を下げる。

## 未決定事項

- 発見レイヤーの探索方法と、採用する記事の基準
- オントロジーのエンティティと関係の設計、および documents スキーマでの表現方法

## 決定事項

- 配信方式（2026-11-13 決定）: 速報の本文は共有 DB に保存し（documents の body）、定時（07:30）に2人のオーナーのエージェントが保存済みの同じ本文をそれぞれのオーナーへ届ける。作成は配信前に作成担当が行う。詳細は docs/morning-digest-runbook.md。
- 速報の意味処理（選定・要約）はエージェント側の工程として行う（タスク化の担い手と同じ 2026-11-12 の決定: 新谷の Muse → Dots → manatago の Muse。VPS から LLM は呼ばない）。

## 実装状況（2026-11-12）

- 取得・登録レイヤーは実装済み（workers/feed_fetch.py、基盤側ワーカーとして xvps 上で常駐し、1時間ごとに取得）。サービス層経由で documents に登録し、ingestion_checkpoints に取得位置を記録する。
- ウォッチリスト初期値は workers/watchlist.json（AI 4媒体＋セキュリティ 6媒体）。入れ替え前提で、見直しは同ファイルの変更で行う。
- 基盤側に意味処理ワーカーは作らない（2026-11-12 の決定で、選定・要約はエージェント側の工程になった）。オントロジー的な整理（エンティティ抽出・関係の付与）は未実装。
- 選定・要約・配信の実行手順書を用意した（docs/morning-digest-runbook.md）。担当順は 新谷の Muse → Dots → manatago の Muse で、どのエージェントでも同じ手順で実行できる形にし、二重作成は documents への morning_digest 登録の有無で防ぐ。Muse は毎朝の定期ジョブで実行している（2026-11-13 設定）。
- 速報の本文の保存先として documents.body を追加した（migration 0004）。documents.ingest で本文ごと保存し、documents.get で取得する。作成と配信の分離（2026-11-13 決定の配信方式）はこの仕組みの上で行う。
